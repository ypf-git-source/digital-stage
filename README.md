# Unity 数字表演演示

一套「语言可控」的数字表演骨架的最小实现。演出本身是数据，代码只负责按时间求值。

两个场景：

- `Assets/Scenes/Performance.unity`：五个演员 + 五盏灯的动画表演，含音频驱动。
- `Assets/Scenes/StageGrid.unity`：10×10 方格阵列拼成的圆形升降台舞台，可直接用中文驱动。

包含两部分驱动：

- **编排 cue**：人工（或将来由语言层）写成的时间轴，驱动 5 个演员和机位。
- **音频 cue**：离线分析一段音频，把节拍和频段变成 cue，驱动 5 盏灯。

## 怎么跑

1. 用 Unity 6.6 打开本工程。
2. 打开场景 `Assets/Scenes/Performance.unity`。
3. 按 Play：音乐响起，灯光跟着鼓点走，演员按编排动作演出。

游戏视图左上角有小控制条：Play / Pause、Replay、Reload cues、进度条。
快捷键：`空格` 播放暂停，`R` 重播，`←/→` 拖动时间，`F5` 重新读 cue 表。

## 演出脚本格式

```json
{
  "t": 0.2,
  "target": "P1",
  "channel": "position",
  "duration": 1.6,
  "easing": "smooth",
  "v0": -4, "v1": 0.5, "v2": 0, "v3": 0,
  "source": "show"
}
```

- `target`：舞台对象。演员是 `P1`..`P5`，灯具是 `L1`..`L5`，另有 `Camera` / `Focus`
- `channel`：`position` | `rotation` | `scale` | `color` | `intensity`
- `duration`：过渡时长，`0` 表示瞬时
- `easing`：`linear` | `smooth` | `in` | `out` | `inout`
- `source`：`show` = 人工编排，`audio` = 音频分析自动生成（重新烘焙时只清这一批）
- `color` 通道用 `v0..v3` 表示 RGBA，`intensity` 用 `v0`，其余通道用 `v0..v2` 表示 XYZ

一条 cue 的含义是「从 t 时刻起，用 duration 秒，把该通道从**它当时的值**过渡到目标值」。
所以动作是叠加式的：写新 cue 不必关心之前的姿态。

## 音频驱动模块

**为什么是离线烘焙，而不是运行时读频谱。** 运行时读频谱拿到的是"这一帧听到什么"，
同一个 t 重播一次结果可能不同，整场演出就不可复现了；而且实时因果检测有个经典陷阱——
周期性的鼓点会把滑动平均阈值顶高，反而检测不到。离线分析可以用全局统计量定阈值，稳得多。
结果落成 cue 之后，音频模块就只是又一个"往 cues.json 追加内容"的来源，播放侧一行都不用改。

**分频段驱动。** 低频给主灯强度（运动），中频给主灯颜色（色彩），高频给细节灯微闪（细节）。
三个频段各自对应不同的视觉通道，互不打架。这是"分层"在 cue 模型里的落地方式：
cue 之间是顺序覆盖关系，不是加法叠加，所以不同层必须落到不同通道或不同对象上。

**怎么生成。** 先用工具脚本合成一段测试音频（刻意做成三个频段互不串扰，这样分频段才验证得出来），
再让 Unity 分析和烘焙：

```
python3 Tools/make_test_audio.py
Unity -batchmode -nographics -projectPath <本工程> \
      -executeMethod DigitalPerformance.EditorTools.AudioCueBaker.BakeFromCommandLine -quit
```

换成真实音乐时，把任意 16-bit PCM 的 WAV 放到 `Assets/Audio/show.wav` 重新烘焙即可。
**不需要重新生成场景**：`BakeFromCommandLine` 只清掉 `source == "audio"` 的旧 cue，
人工编排的 show cue 会原样保留。

## 改演出

- 只改动作：编辑 `Assets/StreamingAssets/cues.json`，回到游戏视图按 `F5` 重新加载，不用重新编译。
- 重新生成整套（场景 + 编排 cue + 音频 cue）：菜单 `Digital Performance / Build Demo Scene`，或

  ```
  Unity -batchmode -nographics -projectPath <本工程> \
        -executeMethod DigitalPerformance.EditorTools.PerformanceBuilder.BuildFromCommandLine -quit
  ```

- 自检（不需要人看画面，验证场景装配、时间轴求值、音频分析与灯光响应）：

  ```
  Unity -batchmode -nographics -projectPath <本工程> \
        -executeMethod DigitalPerformance.EditorTools.PerformanceBuilder.VerifyFromCommandLine -quit
  ```

## 两条时间尺度的位置

主循环固定 1/60 秒求值一次（`PerformanceDirector.quantum`），且每帧都由绝对时间重算。
语言解析、音频分析这类秒级且耗时不定的事**不在**这个循环里——它们只允许往 `cues.json` 写内容。
这就是后面接自然语言入口时，不需要重做任何播放逻辑的原因。

音频虽然是连续信号，但它在这里也是"内容"：分析的产物是离散的 cue，播放时由时间轴统一调度。
`AudioSync` 只负责让 AudioSource 跟随时间轴，并做漂移纠正——时间轴是主，音频是从。

# 场景二：方格升降台舞台

打开 `Assets/Scenes/StageGrid.unity` 按 Play。数字键 1-7 切换预设，`V` 键切换视角（分屏 / 正面 / 侧面 / 俯视），
用 `NLStageBridge` 的 `Submit("...")` 传一句中文就能改舞台。

## 台面几何

台面阵列的尺寸、格距、半径都是 `StageBuilder` 顶部的常数，改完重新生成即可。
当前是 10×10、格距 0.8 米、半径 4 米（舞台直径仍是 8 米）：圆外一共 12 块
（4 个角块，加上 8 块与圆正好相切的退化块——它们的最近点落在圆上，面积是零），
所以实际是 88 块；其中 28 块被弧裁，最小的一块剩 0.203 m²。
台面之间留 2 cm 缝，防止升降时互相刮蹭。

几何对不对可以直接算：圆内所有台面的面积之和必须等于 πR²。
实测 50.256 对 50.265，差值来自圆弧按 2° 离散化，符合预期。

半径决定"圆不圆"和"台面齐不齐"的取舍：取内切值（半径 = 半跨）外轮廓是正圆，
但四角被削光；把半径放大到略大于半跨则方块全在，最小那块也会变大，
代价是外轮廓变成圆角方。这条没有两全解，按需求选。

圆 ∩ 方格是凸的，于是有两个便宜可占：三角化直接从质心拉扇面，不用耳切；
顶点按到质心的极角排序就是正确的逆时针顺序，不用做边界行走。

## 指令模型：图层相加，而不是 cue 覆盖

演员那套是 cue 顺序覆盖，舞台这套必须**相加**——"缓慢整体摇摆 + 一道行波 + 中段中心隆起"
要能同时成立。所以舞台的中间表示是一组带时间包络的**高度场图层**：

```json
{
  "title": "荷叶 · 风起 · 露珠滚落",
  "duration": 14, "loop": true, "base_height": 0.42,
  "layers": [
    { "type": "radial", "channel": "height", "scope": "all", "radius": 3.6,
      "amplitude": -0.18, "start": 0, "fade_in": 2, "hold": 0, "fade_out": 0 },

    { "type": "wave", "channel": "height", "direction_deg": 20, "wavelength": 24,
      "amplitude": 0.22, "speed": 4, "start": 0, "fade_in": 2.5 },

    { "type": "drop", "channel": "height", "direction_deg": 35, "speed": 1.1,
      "radius": 1.6, "amplitude": 0.1, "start": 1.5, "hold": 3.2 },
    { "type": "drop", "channel": "glow", "direction_deg": 35, "speed": 1.1,
      "radius": 1.0, "amplitude": 1, "start": 1.5, "hold": 3.3 }
  ],
  "moves": [
    { "lift": "r3c3", "mode": "set", "height": 1.2, "start": 2, "duration": 1.5 }
  ]
}
```

九种图层：`plane` 倾斜平面、`wave` 行波、`ring` 同心涟漪、`radial` 圆顶或碗、
`steps` 台阶、`noise` 随机涌动（带固定种子，保证可复现）、`drop` 露珠滚过、
`ruffle` 叶缘褶皱（沿角度起伏、只在某一圈附近起作用）、`twist` 绕茎扭转。
`scope` 让语言层说"外圈""中间""左前角"就够，不用报 36 个编号。

每个图层还能指定 `channel`：`height`（默认）进高度场，`glow` 只让台面亮起来、不改变高度。
做露珠时典型的写法是同一轨迹配两条 `drop`——一条抬起一点让它有体积，一条发光让它看得见。

## 荷叶主题

**默认程序现在是空的**：只有台面本身，不带任何效果，也不做任何动作（`空白舞台`）。
效果定义仍在 `StageEffects` 里，HUD 上的效果按钮默认全关——想加回哪一项点一下按钮即可，
它们也可以随意组合叠加。

下面是这套荷叶效果的设计，需要时按按钮打开：

**叶形**是一条常驻的 `radial`，幅度为负，做出中心略低的浅碗。**风**用了两条：
`twist` 让叶片绕茎扭转（周期约 7 秒），`ring` 从叶心向外推波。**叶缘**是 `ruffle`，
14 个波瓣只作用在最外一圈。

**表面上的发光全部去掉了。** 叶心积水的高光、几次呼吸、露珠的闪光与尾迹、
以及更早的光晕，都不再出现在效果库里——现在叶面是一张干干净净、只受灯光影响的表面。
发光通道本身和材质里的自发光接口都还在（`glow` 图层、`StageDirector.ApplySurface` 里的
`_EmissionColor` 写入），`StageEffects` 里也留了注释说明怎么把这几条接回来。

**露珠**只保留形变：一条轨迹上的一段微凹，后面拖一条衰减的尾迹涟漪。

露珠的**方向不是写死的**：`StagePaths` 会把轨迹预先烘焙一遍，每一步沿高度场的负梯度走，
所以它会顺着浅碗的坡、顺着风压出的斜面滚，遇到被手动抬起来的台面还会绕开，最后从最低的那处叶缘出去。
烘焙而不是运行时积分，是为了不破坏"任意时刻都能由 t 独立算出"这条性质。

这里踩过一个坑值得记下来：风是"绕着茎旋转的倾斜"，最初让坡度主导方向时，
珠子被旋转的方向带着绕圈，轨道半径正好等于 速度/角速度（实测约 1.3 米），
永远滚不出去。改成"坡度 × 增益 + 既定方向"再归一化之后，坡度只负责偏转，
珠子既能顺坡摆，又能一路走到叶缘（实测最远 3.94 米 / 半径 4 米）。
另外碗也不能太深——碗底就是积水处，水天然流不出去，所以叶形幅度压到了 0.06 米。

还有一张**连续表皮**可用（`LeafSkin`，极坐标圆盘，24 环 × 96 扇区），**默认关闭**。
它是一张完整的圆盘、盖在台面上方 12 厘米，所以铺上之后俯视会变成一个绿色圆盘、
看不到台面之间的缝——想"看起来像一整片叶子"时按 `T` 打开，想看台面分格时保持关闭。
每个顶点的高度由同一套高度场在连续位置上求值得到，法线每帧重算——所以缝消失了、
叶面看起来是在弯曲而不是一块块升降。台面仍然是驱动源，按 `T` 在"有表皮 / 看台面"之间切换。
表皮比台面顶面抬高 12 厘米，避免台面边角从表皮里戳出来。

## 画面细节

这几条是"从能跑变得耐看"的改动，都不改变机制，只改呈现。

**叶片用了自定义着色器**（`Assets/Shaders/LotusLeaf.shader`）：`Cull Off` 双面渲染，
靠 `VFACE` 判断正反面——叶背用偏暗偏黄的绿、法线翻转，所以从下面看也是对的；
漫反射保留一点补光余量（`saturate(ndl*0.8+0.2)`）但不用纯半兰伯特——那会把明暗拉得太软发闷；
蜡质高光用更紧的高光指数；**逆光透光**是 Standard 做不到的：
光在背面、视线朝着光源时叶片透出浅绿（强度压到 0.35，之前 1.05 太"透"了）；
叶缘按 UV 到中心的距离做 alpha 渐隐，叶子看起来是薄的。

**台面之间不再互相投影。** 88 块台面之间只有 8 毫米缝，如果每块都互相投影，
缝里就是一条条暗线；现在台面既不投影也不接收投影，缝里是干净的，表皮照常投影。

**缝里垫了一层叶色底，缝宽收到 8 毫米。** 四条缝在方块的交点交叉，如果正下方就是深色水面，
每个方块的四角会显出一个黑角。现在台面下方 **5 毫米**处垫了一张同贴图的圆盘（不透明，
用 Standard 而不是叶面着色器，半透明材质做不了底），缝里看到的是叶色；底要贴得近，
槽深了缝看着反而更大。

缝宽的取法有个简单公式：**接缝占比 ≈ 2 × 缝宽 ÷ 格距**，只跟这个比值有关，
跟平台多大、切几格都没有直接关系（平台和阵列同时翻倍，占比不变）。
现在 8 毫米 ÷ 0.8 米 = **2.0%**，比上一版的 14 毫米（3.47%）降了四成。
台面侧面采样贴图中点（叶肉中绿）而不是边缘的深绿，免得露出的侧面偏黑。

**叶缘描边收窄了。** 纹理的边缘压深从"外侧 10% 压到 78%"改成"外侧 4.5% 压到 88%"，
着色器的叶缘渐隐宽度也从 0.18 收到 0.08——之前那一圈太宽，看着像给叶子描了黑边。

**叶面是平的。** 颜色贴图和法线贴图来自同一个高度场。曾经给叶面加过两层噪声
（大尺度缓坡 + 细颗粒）想让它在侧光下有质感，但那在法线上会形成柔和的**波浪状明暗**，
按需求全部去掉了——现在内侧 90% 的高度跨度是 0.0000，只留叶缘轻微上翘。

**光晕已去掉。** 曾经为了替代后处理泛光，在积水和露珠外各叠了一圈大而淡的柔光；
但那一大片柔光会把叶面糊掉，正交俯视下尤其明显。现在只保留紧贴的发光本体，
外圈迅速降到零（实测核心 0.64、r=2 米处 0.00）。
同时把贴图从 1024 提到 2048 并开了各项异性过滤，俯视时叶面更锐利。

**水面用了 `PondWater.shader`**：几道方向不同的正弦叠加，每帧扰动法线，
水面不是一块静止的板。

**运动不再整齐划一。** `jitter` 给相位加一层平滑的空间噪声——全部同相位时波浪像机械波，
加了之后相邻位置各走各的，而因为用的是平滑噪声，表皮仍然是连续的。
`gust` 让幅度随时间缓慢起伏（阵风），`accel` 让露珠下坡加速，`flicker` 让高光闪烁。
这些都是确定性函数，可复现性不受影响。

**换程序会做 0.5 秒交叉过渡**，不是硬切。另外开了 4x 抗锯齿、锁 60 帧，
并加了一盏侧后方补光让叶片轮廓从暗背景里跳出来。

外观是一张程序生成的荷叶纹理（`Assets/Textures/LotusLeaf.png`，极坐标画径向叶脉 + 中心到边缘的渐变）。
关键在于**顶面 UV 用的是舞台坐标归一化**，不是逐块的局部坐标，所以一张纹理铺满整个圆，
叶脉跨台面也是连续的；台面之间 2 厘米的缝正好读成叶脉之间的分格。
侧面统一取纹理边缘那一点，读出来是叶背的深绿，柱子看起来像茎。

**叶脉已按需求去掉。** 只保留叶肉自身的两档起伏（大尺度缓坡 + 细颗粒）和叶缘抬升，
避免叶面变成一块纯色塑料板。叶脉那套实现（18 条主脉 + 两级分叉、蜿蜒的角向慢调制）
在 `LotusTexture.Sample` 里以注释形式保留，需要时可以接回去。

这里有个坑值得记：Unity 的 `Mathf.SmoothStep(from, to, t)` 是在 from 和 to 之间按 t 插值，
**不是** GLSL 那种边缘平滑。我按后者用了一次，结果"主脉/分支"的径向包络完全变样——
主脉在叶心就被削弱、边缘抬升从叶心就开始生效，整片叶子出现径向条纹，正是"西瓜"的观感。
纹理里现在用的是自己写的 `Edge(a, b, x)`。

求值顺序：基准高度 → 各图层相加 → 单台指令覆盖 → 行程夹紧。全部由绝对时间算出。

## 三个会咬人的工程约束

**基准面必须自动抬高。** 人说"波浪起伏"时默认是围绕中间高度上下摆，
但升降台只能从基准面往上走，下半部分会被切平。所以编译时要先算一遍整场的最低点，
把 `base_height` 抬起来——这就是上面那份程序里 base_height = 0.43 的来历。

**机械速度上限才是艺术参数的真正约束。** 行波"快不快"不看相位速度，
而看任意一块台面每秒要移动多少米：

```
变化率 ≈ 幅度 × (2π / 波长) × 相位速度
```

波长越短、幅度越大，看似不快的相位速度也会让台面跟不上。淡入淡出同样算运动，
平滑包络的峰值斜率是 1.5，也要计进预算。`NLStageBridge.ClampForSpeed` 会按这个公式
把参数拉回合法范围；台阶要按"每级高差 × 级数"折算等效幅度。

**方格阵列是离散的，不是曲面。** 空间波长小于 2 米、或在 1 米内做两级台阶，看起来就是噪点。
所以能做好的是：整体倾斜/跷跷板、波长 ≥ 2 格的单双波、同心涟漪、中心圆顶或碗、
单向台阶、缓慢随机涌动。做不了的是：平滑曲面、细节纹样、陡峭的局部造型。

## 自然语言怎么接进来

`NLStageBridge` 有两条路，产物是同一个 `StageProgram`：

1. **调 API**：把舞台描述、可用图元、机械约束和一条示例写进系统提示词，
   用 JSON 模式让模型直接吐高度场程序。模型名和 endpoint 可配，
   key 走环境变量 `OPENAI_API_KEY`（不写进工程）。
2. **本地规则**：没配 key 时用关键词解析兜底，覆盖"波浪/倾斜/圆顶/涟漪/台阶/涌动/复位"
   这些常见说法，并自动按上面的公式收敛参数。

两条路的输出都要过 `StageValidator`：逐帧采样检查行程、速度、相邻高差，
顺便检查波长是否短到会混叠。**模型只能产出中间表示，不能直接驱动机械**——
这是整个设计里最关键的一条线。

## 已知边界

- 分析器只支持 16-bit PCM 的 WAV（不走 Unity 的音频导入设置，直接解析字节，避免导入选项影响结果）。
- 起振检测针对打击性、节拍清晰的素材；连续、无节拍的氛围音乐需要换检测策略。
- 音频 cue 只驱动灯，没有驱动演员。让声音驱动编舞会碰到"同通道顺序覆盖"的限制，
  要做得先引入真正的调制层（基础轨道 + 叠加轨道）。
- 灯光强度是相对值，不能用来推算真实灯具功率；灯光数量和阴影都是关掉的，性能优先。
- 这是演示骨架，不是演出级系统：固定物理步长、随机数种子、硬件时间码、DMX / Art-Net 都还没有。
- 舞台部分是**运动学**模型：只算台面位置，不含伺服响应、载荷、结构变形和联锁。
  真实安全还要加：限位与急停、防夹、人在台上时限速、相邻高差的机械硬限位。
- 舞台的 API 通道没在本机实测过（没有可用的 key 和网络），本地规则那条路是实测通过的。
- 舞台与表演还是两个场景。要把演员放到升降台上，让台面运动和演员动作共用一条时间轴，
  需要把两个求值器接在一起，这属于下一步。
